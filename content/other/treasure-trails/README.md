# Treasure Trails foundation

This module implements a **restricted beginner trail pool**, not complete OSRS Treasure Trails. New trails use 20 initial clues: five native maps, nine native anagrams, four simple NPC cryptics, Charlie's request clue and Reldo's hot/cold clue. The cache supplies clue text, NPC targets and map coordinates; `enum.treasure_trails_beginner_maps` maps the five native clue rows to their existing client interfaces.

Supported behavior:

- After X Marks the Spot, opening a beginner box consumes exactly one box and creates one active scroll. A clue in the inventory, bank, grave or Death's Office prevents another active beginner clue.
- A raw beginner scroll can start a trail before the quest. Trail lengths use 10% / 45% / 45% probabilities for one / two / three steps. The current row, total length, completed steps and generation are permanent server-only varps, reserved at 63510–63513.
- Reading opens the native map or text interface. Digging at the cache target completes a map; Talk-to on the target NPC completes an anagram. A common NPC override hook preserves the existing interaction route and resolves the current morph. It rechecks the claim before dispatch and falls back to normal dialogue if the clue was removed or completed. Conflicting claims fail explicitly.
- The four simple cryptics use the native Hans, Cook, Hunding and Shantay targets. Charlie instead assigns one of all eight native requests on the first conversation. The selected native task row is stored in permanent server-only varp 63514 and cannot be rerolled by reopening the clue or reconnecting. The clue displays the native request text. A later conversation exchanges exactly one carried, unnoted requested item and the active clue for the next clue or final casket in one transaction. Premade items are accepted, matching the December 2022 change; no skill-level or freshly-created-item requirement is added. Banked/equipped/noted items cannot satisfy the hand-in. `enum.treasure_trails_beginner_charlie` supplies the item link absent from the native task rows.
- Reldo's clue selects one of all five native beginner hot/cold destinations. Permanent varps 63515–63517 preserve the target, last measured distance and actual last measurement coordinate. Reldo gives the reusable native beginner device only with space and an active clue; carried/banked devices are not duplicated. Feeling it reports Chebyshev distance bands and warmer/colder/same comparisons without master-device damage. Digging within three tiles on the destination's native plane advances the clue. Neither talking nor obtaining the device completes the step. A pending dig is bound to its coroutine, clue generation and target, then revalidated after the animation. A stale callback cannot solve a new clue at the same spot.
- Supported clues synchronize native `varp.cluehelper_infobox_clue`. With the player's existing helper/infobox options enabled, `interface.helper_generic` opens on the native gameframe helper layer. Charlie's helper changes to the selected native task; the first Reldo device reading changes it to the hot/cold helper. Genuine readings send the native current/previous coordinates and distances, allowing the client to eliminate candidate destinations. This does not alter clue selection or item transitions. A small active-session watcher clears stale presentation after banking, dropping or completing the clue and honors option changes.
- Each successful completion produces either the next scroll or the final beginner reward casket. The item transaction commits before progress changes. Stale generations, vanished inputs, full inventories and overflow cannot award a second output.
- Boxes and active clues share capacity; final reward caskets do not count. Capacity uses the native minor, major and Mimic scroll-case unlock bits. Consuming a case updates its native persistent bit once.
- NPC clue drops use the ownership policy after the existing box transformation. Saved Combat Achievement tier state 2 controls rate improvements; default/unclaimed states do not grant them. This is a reward-state check, not a Combat Achievement task engine.

Material limitations:

- Beginner caskets now have a complete published reward pool, but the under-ten-hour anti-bot replacement distribution remains unverified. For accounts below ten played hours, opening is temporarily declined and the casket retained. This is an explicit parity gap: live OSRS permits opening with restricted rewards. No substitute loot distribution is fabricated.
- Beginner emotes and all higher-tier solutions are outside this pool. Choosing uniformly from the supported pool changes the full OSRS clue distribution. Immediate previous-row exclusion is also an implementation assumption: the Wiki permits repeated clues, but does not establish an adjacent-repeat rule. Charlie's eight requests and Reldo's five destinations are sub-selections of one initial clue each. Equal sub-selection weights are implementation assumptions; their internal server weights are not published. Native clue-helper destination lists are presentation data, not evidence for server sampling weights. Native elite kill-target cache rows were audited but are not assigned or treated as beginner steps.
- Hot/cold measurements use two-dimensional Chebyshev distance, confirmed by native `coord_distance` as well as RuneLite's solver; digging requires the native destination plane. Dynamic-instance normalization, Jagex's exact off-plane device text, retention of previous readings across different clue steps, and replacement-device checks for graves/Death's Office remain unverified. Previous beginner readings reset with the current trail step. Each actual reading updates native shared `varp.trail_hotcold_last_check_coord`; beginner comparison history remains separately stored so another tier cannot corrupt its previous coordinate. Unrelated step changes never reset that shared native varp. Whether live OSRS intentionally shares comparison history between tiers remains unverified.
- Native helper Reset rebuilds presentation from the latest saved reading, Close hides the infobox until another read/step, and Disable changes the native infobox option. Reconnect replays the last actual observation, not fabricated coordinates or the client's discarded full inference history. Exact live helper reset/reconnect behavior is not certified. The implementation honors existing native options and does not force enhanced-client-only controls onto the Java client. Native CS2 signatures and fixed/resizable targets are checked, but visual behavior on the built Vesper client still needs a permitted logged-in session.
- Exact map tiles come from the current cache. Live dig tolerances and NPC dialogue wording have not been validated in a logged-in client. NPC hand-offs currently use a completion message.
- The pickup validator refuses an over-cap stack intact. OSRS's destruction of excess boxes when warnings are disabled is not implemented. Suppression follows the reminder setting, but the associated missed-drop chat notification is still missing.
- Opening a fresh box resets abandoned progress correctly. Ground items currently lack a persistent per-item clue identity; exact progress behavior when abandoning and picking up different raw beginner scrolls, ground persistence across restarts, and OSRS ground lifetimes remain incomplete.
- No higher-tier box-opening workflow is registered. Existing X Marks the Spot quest logic remains in its own module.

The shared pickup fix in `api/obj-plugin` prepares inventory insertion, rechecks visibility, distance, expiry, validators and exact object identity after any animation, and removes the ground item only when insertion can succeed. The synchronous post-commit `onTake` notification is not retried. Hooks must not throw; if one does, remaining hooks run and the committed-action failure propagates without replaying items. Agility uses this notification for its own persistent mark state.

Validation is coordinated from the workspace root:

```sh
./gradlew :content:other:treasure-trails:test :api:obj-plugin:test :content:drops:test :content:quest:test
```

The earlier build on 29 October 2026 passed all 22 Treasure Trails tests, all 8 shared pickup tests and both new Combat Achievement reward-state tests. They exercise trail transitions and save/reload state, inventory conservation, stale callbacks, native capacity bits, NPC morph/fallback behavior, conflicting hooks and delayed pickup. The workspace build receipt records the overall build result. No legal terms were accepted and no logged-in gameplay smoke test was performed for this module.

## Beginner casket implementation

`BeginnerRewardsTable.kt` packs all **74 published item outcomes**, with no missing/empty substitute branch. The generated `TreasureTrailsBeginnerRewardsRow` supplies the item, pool, integer weight, inclusive quantity bounds and noted flag. All referenced item symbols were resolved against the local revision-241 cache. No native named reward table was found; native clue-helper tables describe clue steps rather than reward odds.

| Pool | Outcomes | Weight per outcome / 44,280 | Published probability per reward roll |
| --- | ---: | ---: | ---: |
| Beginner uniques | 15 | 123 | 1/360 |
| Black equipment | 18 | 55 | 11/8,856 |
| Ordinary equipment, runes, arrows and food | 40 | 990 | 11/492 |
| Noted cabbage | 1 | 1,845 | 1/24 |

These weights sum exactly to 44,280. This is algebraically equivalent to the published rare and black sub-tables; the rare items are not replaced by a convenient subset. There are one to three reward rolls. The implementation uses a uniform roll-count draw and uniform inclusive quantity draws; the Wiki states the range and mean, but those internal RNG distributions have not been independently traced in Jagex's server code. The table does not add a master clue or any unlisted reward.

Opening, rather than receiving the final casket, increments native permanent `varp.completed_clues5` and `varp.completed_clues_total`. The collection log is credited during that same synchronous opening action, including rewards destined for the ground. Minor/major case thresholds (50/100) come from `enum.treasure_trails_beginner_cases`. Existing carried/banked/grave/Death's Office cases are not duplicated; missing unconsumed cases are reissued. Case capacity only increases when the existing case-use handler consumes the case and sets its native bit. Native `varbit.emote_explore` unlocks at 600 openings, including an existing account above that threshold. No quest or higher-tier clue progression is granted by opening a casket.

The casket and its exact rolled rewards are exchanged in one inventory transaction using `inv.vesper_beginner_reward_pending` (Perm, Normal, 12 slots). Normal stacking is intentional: this engine automatically unnotes items in Always-stack containers. The journal keeps the native noted form of food and cabbage. Each entry transfers atomically to inventory; any remainder is registered as ordinary owner loot before the corresponding journal deletion commits. No suspension or subsequent acceptance check occurs between ground registration and commit. A rejected ground registration leaves the complete entry pending, including the portion which could fit in inventory. Login or the next casket interaction retries delivery without rerolling, consuming another casket, incrementing completion or logging the same reward again. No extra claim interface is introduced.

The journal uses normal character persistence. It does **not** make ordinary ground items durable across server crashes/restarts, or eliminate the engine's general autosave rollback window. Already-delivered ground loot follows the existing repository ownership, reveal and expiry rules; exact live overflow-lifetime parity is not certified. These limits apply to the implementation rather than being claimed OSRS mechanics.

Presentation uses the native `interface.trail_rewardscreen` and its `items` component. Native CS2 reads `inv.trail_rewardinv` automatically. The server sends a detached packet snapshot with that native inventory type and keeps its display-only copy in Temp `inv.vesper_beginner_reward_display`. It never places clue display items in the player's real `inv.trail_rewardinv`, because Barrows transfers that inventory on logout. Closing/examining the clue reward screen cannot award items. The existing Barrows flow remains separate.

The surface Entrana region pair from RuneLite is blocked; Entrana Dungeon remains allowed, as the Wiki explicitly specifies. The implemented surface rectangle is x2752–2879, z3328–3391, including upper floors. RuneLite's geographic regions are evidence for location, not proof of the exact Jagex casket script boundary. Law Altar and dynamic-copy normalization are still unverified. No live client acceptance or login was performed for this work.

New tests cover every weighted outcome and quantity endpoint, noted conversion, stale/vanished inputs, stacked caskets, counter overflow, collection-log timing, full inventories, partial stacks, ground merges and maximum stacks, rejected registration, save/reload recovery, case awards/consumption, Explore, and isolation from Barrows's logout inventory.
